# 实际调用治理：共享并发池、发送生命周期与诊断一致性

日期：2026-09-25。基线：`main@17b7dc925a1a0e00ba81dc4afd008f6e5983c205`。
范围：把已存在但相互独立的调用规则接入真实业务路径，修复取消、授权、账本和响应校验边界。没有修改真实书籍、私有配置或密钥，没有重启日常服务、调用收费模型。

## 1. 真实问题与改动

原 `QwenRequestGate` 和 `ProviderResourceRegistry` 各有自己的计数与等待队列。辅助、自检、手稿走前者，旧Qwen OCR和通用调用走后者，可能叠加准入；诊断仅查询后者，无法反映现代Qwen路径的真实占用。

现在 `QwenRequestGate` 仅是共享 `ProviderResourceRegistry` 的兼容门面。Spring构造器要求同一注册表与实际调用服务，不在生产装配时创建第二份池。统一上限3、后台最多2、等待队列最多24；缩容计入旧在途请求，等它们自然结束，不强杀重发，也不因重新配置增发许可。

等待过程每100ms以内检查取消标志；不要求其他请求完成或外部发送线程中断才能取消。原绝对期限不重置，过期的等待者不能在唤醒时抢到刚释放的槽位。

`PhysicalCallService` 现在提供真实被调用的流式入口 `openQwen`。Qwen整页辅助、结构整理、文字分组核对、目录恢复、手稿转录、自动可理解性自检经 `QwenPhysicalCall` 委托给同一 `PhysicalCallSession`，不再各自维护两套发送与结算状态机。通用缓冲式 `execute` 同样使用该会话。

## 2. 一次发送的所有权

准备、排队及未发送不等于一次收费调用。顺序为：检查条件 → 获取共享并发许可 → 预留原页级预算 → 持久PREPARED → 构造请求并验证 → 持久SENT_UNKNOWN → 再检查授权、取消、期限 → 真正进入传输。

预算继续继承同一个 `PageAttempt` 的 `QwenExecutionScope`，没有因为引入共享服务再创建另一份8次预算，也没有同时占用两个并发池。旧预算预留接口加同步保护，避免close与markSent并发导致“退还之后仍发送”。

无请求、准备失败、取消或授权撤销发生在传输前：记录NOT_SENT，归还本次未发送预留。进入传输后失败/结果未知：不退款、不由共享服务自行重发。响应流关闭、账本结算后才释放对应许可。

接收到2xx响应头并不代表成功。必须消费本次拥有的完整响应、执行客户端校验，且没有取消/过期，才能声明成功；其他请求的响应不能拿来结算当前调用。非2xx完整响应也不能被手动标成功。

返回的用量先记录，业务验证失败不抹除已知token；未知费用保持未知。账本结算异常只给出固定脱敏诊断，不用“假定已成功”或重发来修补。

## 3. 授权、响应与限流

真实Qwen入口在准入前、请求准备后以及持久发送意图之后复核最新中央授权；撤销和到期不会被旧预约越过。区分当前页增强与邻页增强权限。请求仍受既有目的地址规则保护，未装配必需账本/授权则不发送。
通用缓冲式入口要求调用命令与实际UsageContext的书、页一致。生产装配时调用者必须提供业务校验器；不接受仅凭HTTP 200或任意JSON就宣布模型业务成功。无校验器的兼容重载仅用于显式隔离测试。

`BoundedHttp.Response` 只增加可选Retry-After字段，原两参数构造保留，不复制其他可能敏感的响应头。429等待使用供应商实际值；超过本地允许等待范围、溢出数字或多个矛盾字段时，延期处理而不是截短后提前重试。返回RetryEligible前已释放许可，原调用总期限仍保留。调用服务不自动执行重试。

异常消息不直接透出传输、请求工厂或验证器的原始内容；已知本服务产生的安全原因可展示，其余只返回固定脱敏说明。默认自动自检、已确认策略下自动随读、当前页优先、人工版本保护都保留，无新增用户配置开关。

## 4. 诊断是实际进程占用，不是账户账单

`/api/diagnostics` 保留原qwenInFlight等字段，同时提供每个池在同一锁内捕获的在途数、后台在途数、队列、配置上限、峰值和准入次数。兼容字段来自同一次快照，不会与明细相互矛盾。

返回明确标记PROCESS_WIDE，不返回密钥、账户指纹、正文或本地路径。admittedPermits仅表示拿到许可次数，不等于发送次数、收费次数或可退款次数；费用仍以账本及供应商对账为准。

## 5. 回归与验证方法

新增PhysicalBoundaryRegressionTest覆盖原8项复现与17项集成/反例，并追加4项取消传播／中断收尾回归，共29项。旧生产代码上原8项全部未满足预期，其中7项断言失败，1项因取消未被及时观察触发TimeoutException；不是8个纯断言失败。

额外覆盖实际Spring装配共享池、六种Qwen用途委托、混合适配器缩容、授权在准备后/持久化中撤销、无合法书页上下文、目的地址拒绝、诊断计数一致、账本写失败、业务验证失败保留token、真实Retry-After、原期限剩余量及禁止错误响应成功结算。模型传输全部是受控替身。

保留现有Qwen预算和流关闭测试；原源代码探针顺着Qwen兼容门面检查新的PhysicalCallSession，未删除发送前持久化断言。超长Retry-After原测试改为“不得提前重试”的更严格期望。

首次完整本机测试因清理环境变量时PATH遗漏nvm的Node目录，两个导出/离线脚本测试无法启动node；这是环境失败，不按通过统计。修正为显式Java17和已有Node路径后重新完整执行。

本机Chrome在原前端上也复现关闭原生任务对话框后立刻测量到旧布局：初始reader高度0、底栏仍有250px侧栏偏移；两个绘制帧后布局恢复正确。测试改为最多3秒按绘制帧等待相同几何契约，再断言，额外要求底栏left=0/right=viewport。没有放宽像素误差、加固定睡眠或修改生产CSS来绕过失败；这只修复验收时机，不宣称改善了渲染性能。

## 6. 未完成项与使用边界

本次统一的是现代Qwen调用生命周期及进程级Qwen并发入口。旧Qwen OCR已通过同一注册表计入占用，但仍使用旧传输；Paddle、PP-OCR、JEV、MiniMax的业务入口尚未全部改为共享PhysicalCallSession。异步远端任务债务与本地HTTP占用仍是不同资源，不能简单把两者相加当作一个计费数。

全账户/凭据级容量隔离、所有供应商共用持久预算、预算生命周期归档、完整DelayedCallQueue调度治理、所有模型响应业务校验统一仍未完成。内存预算不代表跨重启的恰好一次调用保证；供应商无幂等证据时，结果未知仍需核验，不能自动补发。

来源日志检查点、真正索引增量事务、手稿按区域立即发布及只续缺失区域、自检未完成组续处理、真实手稿逐字准确率、实际模型费用、大型扫描PDF压力、Safari/Windows真机和硬件断电仍需后续专项。此次不将整份FINAL规范标记为完成。

本批不引入新的运行数据格式，不要求修改密钥或新增自检开关。使用最新main前仍应备份私有数据并正常重启；本次开发只启动隔离测试服务，不代替用户重启日常服务。代码合并和分支清理状态以最终远程核验为准。

## 7. 本次继续执行时追加的中断修复

接续已有未提交工作后，先重新执行原979项完整回归（977通过、2项原有样本跳过）。随后追加4项用例，均在接续版本上断言失败、0执行错误：请求工厂中断、缓冲传输取消、业务验证中断、带中断标志进入未发送回执结算。

原因一：通用execute把InterruptedException和BoundedHttp的CANCELLED当作普通失败/未知返回，丢失取消控制信号；调用方可能误把它交给普通失败处理。现在明确传播CancelledException；InterruptedException清除的线程中断标志会恢复。已经进入传输的预算仍不退款。

原因二：线程已有中断标志时，最终账本的FileChannel写入会被立即打断，明明没有发送的记录也可能一直留在PREPARED。PhysicalCallSession只在清理与持久结算期间暂时清除此已有标志，所有权、预算、许可完成收尾后恢复；不清除业务取消、不重新发送，也不以此声称真实磁盘错误或反复外部中断一定可恢复。

新增测试同时检查请求次数、账本实际终态、预算余额、并发释放与中断标志，不能仅靠捕获异常来通过。原失败证据与接续源码快照保存在仓库外physical-unification-closeout-20260925目录。最终PR/合并后main的实际CI产物才是发布依据。
