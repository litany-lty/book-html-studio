# 旧 Qwen OCR 与 MiniMax：实际调用边界整改

日期：2026-09-25。基线：`main@c7d11bb659d2ddabb07a1feb58457bcea91a7d40`。
本批基于独立工作树开发，不改动真实书籍、运行配置或凭据，不重启日常服务，不调用收费模型。

## 1. 已确认问题

新增首批10个用例在旧实现上全部断言失败、0执行错误。初次试验中一项因账本列表为空而发生索引异常；改成先断言记录数量后重新运行，得到上述10项纯断言失败的复现。

- 两个适配器在资源池返回null、没有取得许可时仍执行发送。
- Qwen普通识别内部隐藏三次429重试，不经过逐次共享预算且占着原许可等待。
- MiniMax尝试写账本，但供应商白名单没有minimax，异常被忽略后继续请求，实际调用可能完全不入账。
- MiniMax在检查业务错误和结构之前标记成功；后续失败无法改写已经成功的终态。
- Qwen只拒绝length，过滤结束或多结果仍可能被接受；非法坐标数组中的非数字被忽略后仍可能拼出一个框。
- Qwen传输的InterruptedException被普通异常包装，取消信号与中断状态丢失。

## 2. 已实施的调用整合

Qwen普通OCR、JEV局部复识别及MiniMax结构辅助均接入`PhysicalCallService.invokeSynchronous`，使用与现代Qwen相同的`PhysicalCallSession`，不另外实现发送、读流和结算状态机。

生产构造器必须提供共享服务。默认传输复用单个延迟初始化的`BoundedHttp`，限制完整响应体大小、总期限和取消，禁止自动重定向；不再每次new HttpClient并无限制地接收字符串。旧字符串Transport构造器仅用于包内隔离测试，不是生产网络路径。

取得并发许可、预留预算、持久PREPARED、持久SENT_UNKNOWN、再次授权/取消/期限校验之后才进入传输；无法记账就不发送。发送后的未知/失败不退款，不通过重发修复未知结果。

同一次页级执行增加独立的5次Qwen OCR物理调用预算，拆页和区域补识不能刷新它；MiniMax与现代Qwen辅助、自检共用原有8次增强预算。两者仍按各自命名的阶段期限约束，不以每个区域重新起表。这里不是所有供应商的跨重启持久预算已经统一。

429每次方法调用最多发送一次，不在适配器内部重试；返回保守的等待说明。再次处理仍需原有任务入口及授权，不新增自动收费入口。

## 3. 结果与账本一致性

两个适配器必须取得本次完整响应，并通过业务解析后才能保存成功回执。正常结束的空words_info继续抛出专用OcrNoTextException，物理请求可记已完成，但上层不得据此推断图像为空白。错误、过滤、截断、多个结果、工具调用或缺少必要OCR字段不当作完整正文。

Qwen原生协议与MiniMax文本协议复用ModelCompletion的单一正常完成检查；严格拒绝重复JSON键、尾随JSON和非法坐标值。MiniMax继续只重组给定来源行，缺失来源会补回，不用模型内容覆盖原文；原有人工覆盖与版本保护不变。

MiniMax现可进入UsageLedger的受控供应商集合，成功、失败和返回用量可在重新加载后读取；内容失败不抹除已知token，也不把未知费用填成0。费用页面增加MiniMax名称。未新增MiniMax计价配置，缺少价格时费用仍为未知。

目的地址策略补齐仓库已有默认`https://api.minimax.cn/v1`的精确主机和HTTPS标准端口，不允许任意*.minimax.cn，也不自动放行用户配置的其他域名。本批不宣称完成DNS重绑定、全供应商目的地址或账户级安全审计。
